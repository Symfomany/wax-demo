LLM Watch Harness

Une veille LLM / GenAI factuelle et sourcée, produite par des agents LangGraph sur un petit modèle local (Ollama, gemma-3-4b-it), et encadrée par un harness : règles, skills, sous-agents, hooks, guards et mémoire, côté application comme côté Claude Code.

4collecteurs parallèles, dont 1 via MCP
2serveurs MCP : GitHub et Notion
3sous-agents (sous-graphes LangGraph)
3niveaux de mémoire
5couches de guards
150tests verts (unitaires, graphe, chat, E2E) + 1 live
≈ 70 spar run complet sur RTX 3070 Ti

Le principe en une phrase

Le LLM choisit et rédige ; le code garantit. Le modèle ne renvoie jamais une URL, un titre ou une date : il désigne des documents par leur numéro, et le code recopie les métadonnées depuis la collecte. Tout ce qui peut être vérifié sans LLM l'est de façon déterministe (dates, URLs, secrets, schémas, budgets), et chaque leçon humaine récurrente est vouée à devenir une règle.

LLM Ce que fait le modèle

Sélectionner les signaux (Scout), juger leur fidélité à la source (Critic), rédiger le digest en français (Editor).

Code Ce que garantit le harness

Métadonnées, schémas Pydantic, dédoublonnage, fraîcheur, guards de publication, budgets, reprise après crash.

Humain Ce que décide l'humain

Publier ou rejeter chaque digest ; sa note devient une leçon mémorisée et réinjectée.

Usage

Démarrage rapide

Prérequis : WSL 2 ou Linux, Python 3.12, Ollama avec un modèle local (testé avec gemma-3-4b-it sur RTX 3070 Ti, 8 Go).

  1. Installer les dépendances 
    cd ~/llm-harness
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
  2. Configurer : copier .env.example en .env et vérifier le modèle. 
    cp .env.example .env
# dans .env : le nom exact affiché par `ollama list`
LLM_MODEL=gemma-3-4b-it
  3. Diagnostiquer : Ollama, modèle, GPU, sources, serveur MCP, migrations, Store. 
    .venv/bin/python -m app.main doctor
  4. Lancer une veille : le run s'arrête avant publication et affiche le digest. 
    .venv/bin/python -m app.main run
  5. Valider ou rejeter : la note est mémorisée pour les runs suivants. 
    .venv/bin/python -m app.main resume <run_id> --approved --note "Garder le focus inférence"
.venv/bin/python -m app.main resume <run_id> --rejected --note "Écarter les tutoriels"

Résultat : output/digest-AAAAMMJJ-HHMMSS.md et .json (conforme au modèle Digest), trace en base SQLite et mémoire mise à jour.

Exemple de sortie réelle

supervisor fan-out : collect:rss, collect:arxiv, collect:github_releases, collect:github_mcp supervisor délègue prefilter → prefilter supervisor délègue research → research supervisor délègue review → review supervisor délègue editorial → editorial supervisor plan terminé → validation LLM : 5 appel(s), 0 depuis le cache SQLite Digest prêt pour validation humaine.

Supervisor & Task Graph

Le Task Graph est une donnée, pas du code : une liste de tâches avec leurs dépendances, validée par Pydantic (ids uniques, dépendances existantes, absence de cycle). Le supervisor lit l'état d'avancement, choisit les tâches prêtes et délègue avec Command(goto=…). Chaque worker lui rend la main.

Patterns conditionnels du supervisor

ConditionDécisionBorne
Plusieurs tâches collector prêtesFan-out parallèle : un Send("collector", …) par sourceune fois par plan
Une tâche prête (ordre du DAG)Délégation séquentielle à l'agent de la tâche—
Moins de MIN_ACCEPTED signaux acceptés et des candidats non évaluésRelance de research avec un seuil de pertinence abaissé de 2 (minimum 3), puis nouvelle revueMAX_REVIEW_ROUNDS = 1
Tâche obligatoire en échec (agent)failed : run arrêté, erreurs tracées—
Tâche optionnelle en échec (source)On continue avec les autres sources—
Plan terminé avec violations des guardsblocked : rien n'est publié—
Plan terminé sans violationapproval → publish ou reject → reflect—

Sous-agents

Chaque sous-agent est un sous-graphe LangGraph avec son propre schéma d'état. Le nœud parent lui passe uniquement ce dont il a besoin et n'en extrait que le résultat : aucune clé à réducteur ne fuit vers le graphe parent (voir Dépannage).

research Map-reduce de Scouts

fan_outun Send par lot de SCOUT_BATCH_SIZE documents
→
scout_batch ×NScout LLM en parallèle ; un lot illisible est ignoré
→
rankseuil de pertinence, dédoublonnage par URL, top MAX_SIGNALS

Le Scout reçoit les critères du Skill veille-tech et la mémoire (leçons + thèmes privilégiés). Il ne renvoie que doc_id, des scores et une phrase ; un doc_id hors du lot est rejeté.

review Pré-contrôle puis Critic

precheckrisques déterministes ; date future ⇒ drop sans appel au LLM
→
criticseulement s'il reste des signaux à juger
→
decidekeep / drop / needs_review ; pas de verdict ⇒ needs_review

editorial Rédaction, guards et réparation bornée

editorrédige à partir des seuls signaux acceptés
→
guardsgarde-fous de publication
→
repairsi violations et budget : réécriture avec la liste des corrections exigées
↺
guardsrevérification ; au-delà de MAX_REPAIR_ROUNDS ⇒ blocked
Repli extractifSi l'Editor omet un signal accepté, son résumé est remplacé par un extrait de la source plutôt que d'être inventé.

Guards : cinq couches

Du plus proche de l'extérieur au plus proche de la publication. Aucune ne dépend du bon vouloir du modèle.

CoucheMécanismeCe qui est bloquéOù
Claude CodeHook PreToolUse (code de sortie 2)rm -rf, SQL destructif, git push --force, lecture ou écriture de .env, secrets dans un fichier, curl | sh, outils MCP d'écriture.claude/hooks/guard.py
MCPIntercepteur tool_interceptors de langchain-mcp-adaptersOutils hors liste blanche ; perPage borné à 10 ; requêtes trop longues ; journal d'audit de chaque appelmake_mcp_guard
LLMEntrées neutralisées ; sortie contrainte par un schéma JSON et validée par Pydantic ; budgetInjections de prompt dans les sources ; JSON invalide (une relance avec l'erreur) ; plus de MAX_LLM_CALLS appelssanitize_untrusted, StructuredLLM
LangGraphRetryPolicy, error_handler, contrats d'état, recursion_limitErreurs transitoires (relancées) ; crash d'un agent (transformé en état puis en failed) ; clé d'état non prévue ; boucle infiniegraph.py, node_contract
PublicationGarde-fous déterministes avant approvalURL absente de la collecte, URL inventée dans le texte, date future, motif de secret, digest videapp/harness/hooks.py

Exemple : contrat d'état d'un nœud

class PrefilterUpdate(_Contract):      # extra="forbid"
    status: dict[str, str]
    candidates: list[dict]

@node_contract(PrefilterUpdate)
def prefilter(state): ...                # écrire "approval" ici ⇒ GuardViolation

Exemple : échec d'un agent

def agent_failed(state, error: NodeError) -> Command:
    # le handler ne suit pas les arêtes du nœud : il rend la main au supervisor
    return Command(goto="supervisor",
                   update={"status": {error.node: "failed"}, "errors": [...]})

Mémoire : trois niveaux

1 Mémoire factuelle · SQLite

data/watch.db : documents collectés, digests, items publiés (jamais reproposés), retours humains, cache des réponses LLM, historique des runs. Schéma versionné par PRAGMA user_version (v2) avec migrations testées.

2 Mémoire des agents · Store LangGraph

data/memory.db (SqliteStore), injectée dans les nœuds (store: BaseStore). Espaces : lessons, tags (thèmes renforcés ou pénalisés), sources (succès et échecs par collecteur).

3 Mémoire Claude Code

Export Markdown du Store dans .claude/memory/veille.md, importé par CLAUDE.md via @.claude/memory/veille.md. Le hook SessionStart ajoute l'état des derniers runs.

Cycle de vie d'une leçon

  1. Un run produit un digest. L'humain le rejette : --rejected --note "Écarter les cours et tutoriels".
  2. L'agent reflect enregistre la leçon dans le Store, pénalise les thèmes du digest et exporte veille.md.
  3. Au run suivant, la leçon figure dans les prompts du Scout et de l'Editor (section « Mémoire de veille »).
  4. Toute nouvelle session Claude Code la voit aussi, via l'import dans CLAUDE.md.
  5. Si le modèle ne suit la leçon qu'en partie, elle devient une règle déterministe (ex. exclude_keywords du collecteur MCP) avec son test.
Cas réel observéAprès la leçon « écarter les cours », gemma-3-4b a retiré ai-engineering-course mais gardé llm-master, une feuille de route d'apprentissage. L'étape 5 a été appliquée : les deux dépôts sont désormais exclus dès la collecte.

MCP GitHub : découverte de dépôts open source

Un serveur MCP github-scout (FastMCP, transport stdio) expose trois outils en lecture seule. Ils portent les mêmes noms que ceux du serveur officiel github/github-mcp-server, ce qui permet de basculer de l'un à l'autre. Le même serveur sert l'application (via langchain-mcp-adapters) et Claude Code (via .mcp.json).

OutilArgumentsRenvoie
search_repositoriesquery, perPage (≤ 10 après guard), sortnom, URL, description, étoiles, langage, topics, licence, dates
list_releasesowner, repo, perPagereleases publiées (brouillons exclus)
get_readmeowner, repo, maxCharsextrait texte du README (404 toléré)

Dans le pipeline

La tâche collect:github_mcp ouvre une seule session stdio, lance une recherche par requête de [github_mcp] (bornée par une date de création calculée, jamais inventée), exclut les dépôts qui correspondent à exclude_keywords, lit le README des mieux étoilés, le nettoie (badges, liens, injections) puis crée des Document à partir des seules valeurs renvoyées par l'API.

[github_mcp]
enabled = true
lookback_days = 21          # created:>aujourd'hui-21j
min_stars = 100
per_query = 5
max_repos = 8
queries = ["llm inference", "agent mcp", "rag retrieval", "llm evaluation benchmark"]
exclude_keywords = ["tutorial", "course", "roadmap", "awesome", "interview", ...]

Usage direct

.venv/bin/python -m app.main github "agent mcp" --limit 5   # via l'app
claude  # puis : « utilise le sous-agent github-scout pour les nouveaux repos RAG »
Quota GitHubSans jeton : 60 requêtes/h (API REST) et 10 recherches/min. Définir GITHUB_TOKEN dans .env (lecture publique suffisante). Le jeton n'est transmis qu'au processus du serveur MCP.
Passer au serveur GitHub MCP officiel

Le serveur officiel s'exécute via Docker ou en service distant et nécessite un jeton d'accès personnel. Il suffit de remplacer la connexion renvoyée par stdio_connection() dans app/collectors/github_mcp.py et l'entrée de .mcp.json : les noms d'outils search_repositories et list_releases sont communs. Le guard MCP continue de n'autoriser que la lecture.

Rapports datés & Notion

La publication d'un digest déclenche une suite d'outils de publication (app/publishers.py). Seuls les fichiers sont critiques : un échec du rapport ou de Notion est consigné dans les erreurs du run sans annuler la publication.

fichiersJSON + Markdown + mémoire SQLite critique
→
rapportreports/AAAA/veille-AAAA-MM-JJ-HHMM.md
→
notionpage des 10 dernières veilles (si configuré)

Le rapport daté

Rendu par Jinja2 depuis templates/report.md.j2 : front matter YAML (titre, date, run, modèle, mots-clés), « En bref », tableau de synthèse, « À retenir », une fiche par signal (source, date, lien, résumé, pourquoi c'est important, tags), table des ressources, écartés par le Critic, méthodologie et trace du supervisor. Mots-clés déterministes : tags thématiques, puis mots récurrents des titres. python -m app.main report le régénère.

La page Notion

Serveur MCP notion-veille (app/mcp_servers/notion_server.py) appelé via langchain-mcp-adapters. Pour chaque veille : titre (titre 2), résumé (encadré), description, ressources (liens), mots-clés. Découpage par 100 blocs, ancienne page archivée. Le guard notion_policy limite l'écriture à la page parente configurée et aux pages créées par la veille.

Pourquoi pas le serveur officiel pour publier ?Dans sa version 2.5.2, le schéma de blocs de @notionhq/notion-mcp-server pour children se limite aux paragraphes et puces. Il reste déclaré dans .mcp.json pour explorer Notion depuis Claude Code.

Exploitation

Observabilité

  • Terminal : décisions du supervisor, erreurs par source, appels LLM et cache.
  • SQLite : table runs (statut et statistiques JSON, y compris la trace), sqlite3 data/watch.db "SELECT status, stats_json FROM runs".
  • Langfuse (optionnel) : LANGFUSE_ENABLED=true et clés dans .env. Callbacks sur chaque run de veille et chaque tour de chat ; regroupement par langfuse_session_id (run ou conversation), tags veille / chat.
  • LangSmith (optionnel) : LANGSMITH_TRACING=true et clé dans .env, recopiées dans l'environnement du processus ; vue Threads via la métadonnée session_id.
  • Guide pas à pas pour analyser les conversations : Getting started, étape 8.
Exploitation

Dépannage

doctor : « Modèle … absent »

Le nom de LLM_MODEL doit correspondre exactement à ollama list (ex. gemma-3-4b-it). Corriger .env ou surcharger ponctuellement : LLM_MODEL=gemma-3-4b-it python -m app.main run.

arXiv renvoie HTTP 406

L'API export.arxiv.org limite fortement les requêtes rapprochées. Le projet utilise les flux officiels rss.arxiv.org, plus stables pour une veille quotidienne.

GitHub : 403 ou 429

Quota anonyme atteint. Définir GITHUB_TOKEN. La source est marquée en échec dans la mémoire (santé des sources) et le run continue avec les autres.

Run « bloqué par les guards »

L'Editor a écrit une URL ou une date non traçable, et la réparation n'a pas suffi. Les violations sont affichées et stockées dans runs.stats_json. Relancer avec --no-collect (les appels du Scout sont servis par le cache).

Pièges LangGraph rencontrés pendant le développement
  • Sous-graphe comme nœud direct : s'il partage une clé à réducteur operator.add avec le parent, il renvoie la liste entière, qui double à chaque passage : explosion mémoire (processus tué). D'où des états séparés et des nœuds d'adaptation.
  • error_handler et Send parallèles : dans la version utilisée (LangGraph 1.2.12), le handler n'intercepte pas l'échec d'une tâche quand ses voisines parallèles réussissent. Les collecteurs isolent donc eux-mêmes leurs erreurs.
  • Après un error_handler, les arêtes du nœud en échec ne sont pas suivies : le handler doit renvoyer Command(goto="supervisor").
Le modèle ne suit pas une leçon

Un modèle de 4 milliards de paramètres applique les consignes de façon partielle. Transformer la leçon en règle déterministe (filtre, guard) et ajouter un test ; voir le cycle de vie d'une leçon.

Transparence

Limites connues

  • Avec gemma-3-4b, le Critic est parfois indulgent et l'Editor peut paraphraser au-delà de l'extrait ; les guards bloquent les URLs, dates et secrets, pas les nuances de formulation. La validation humaine reste la dernière barrière.
  • Le supervisor est déterministe (règles sur l'état) : un routage par LLM serait possible, mais moins fiable avec un petit modèle.
  • Le dédoublonnage repose sur l'URL et le titre normalisé ; il n'y a pas encore de similarité sémantique (embeddings).
  • .mcp.json contient des chemins absolus propres à cette machine.
  • L'état des veilles lancées depuis l'interface est gardé en mémoire du serveur : après un redémarrage, un run en attente se reprend avec python -m app.main resume.
  • La relance de research réévalue tous les signaux (appels du Scout servis par le cache, mais nouvel appel du Critic).
