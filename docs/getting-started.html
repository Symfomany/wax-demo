Getting started · WSL 2 · GPU local

De zéro à votre première veille

Démarrer Ollama et le modèle local, lancer la veille en ligne de commande ou dans l'interface de chat, vérifier que tout fonctionne, puis brancher Notion, Langfuse et LangSmith.

En 5 minutes

ollama serve &                                  # 1. le serveur LLM local (si pas déjà en service)
ollama run gemma-3-4b-it "Réponds OK"            # 2. le modèle répond sur le GPU
cd ~/llm-harness && source .venv/bin/activate
python -m app.main doctor                        # 3. tout doit être OK
python -m app.main web                           # 4. http://127.0.0.1:8000
À vérifier une foisDans .env, LLM_MODEL doit porter le nom exact affiché par ollama list (ici gemma-3-4b-it). doctor signale l'écart s'il existe.
Étape 1

Démarrer Ollama et le LLM local

Vérifier le GPU dans WSL

nvidia-smi          # doit afficher la RTX 3070 Ti et la mémoire (8 Go)

Démarrer le serveur Ollama

Service systemd (installation standard)

sudo systemctl start ollama
systemctl status ollama --no-pager

Nécessite systemd dans WSL ([boot] systemd=true dans /etc/wsl.conf).

À la main, dans un terminal

ollama serve

Laisser le terminal ouvert ; ou ollama serve & en arrière-plan.

Vérifier l'API et le modèle

curl -s http://127.0.0.1:11434/api/tags | head -c 300   # l'API répond
ollama list                                            # gemma-3-4b-it, qwen:latest…
ollama run gemma-3-4b-it "Donne trois usages d'un LLM local."
ollama ps                                              # PROCESSOR = 100% GPU

Le modèle reste chargé quelques minutes après le dernier appel ; le premier appel d'une session est plus lent (chargement en mémoire GPU, environ 30 à 40 s mesurées ici).

Modèle installéCapacités OllamaUsage dans le projet
gemma-3-4b-itcompletionModèle par défaut : sorties JSON contraintes par schéma, réponses du chat
qwen:latest (qwen3 4B)tools, thinking, completionAlternative à comparer : LLM_MODEL=qwen:latest python -m app.main run
Pas de « tool calling » natif nécessaireLe routeur du chat et les agents utilisent la sortie structurée (schéma JSON imposé par Ollama) : tout modèle « completion » convient.
Étape 2

Installer le projet

cd ~/llm-harness
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
cp -n .env.example .env        # -n : ne jamais écraser un .env existant
python -m app.main doctor

doctor contrôle : Ollama, présence du modèle, GPU, sources déclarées, serveur MCP github-scout, Skill, migrations SQLite, Store LangGraph, .gitignore et Langfuse. Il renvoie le code 1 si un contrôle échoue.

Étape 3

Quoi lancer

💬 Interface web de chat

python -m app.main web puis http://127.0.0.1:8000. Chat sourcé, onglet Veille (lancement + validation), Rapports, Mémoire.

⌨️ Ligne de commande

python -m app.main run, puis resume <run_id> --approved --note "…". Le rapport daté et la page Notion sont produits à la publication.

🤖 Claude Code

Ouvrir le dossier dans Claude Code et taper /rapport-veille : le skill déclenche doctor → run → audit → resume → report → notion-sync → memory.

Ce que produit une veille publiée

SortieEmplacement
Rapport Markdown daté (front matter, synthèse, à retenir, signaux, ressources, écartés, méthodologie)reports/AAAA/veille-AAAA-MM-JJ-HHMM.md
Digest JSON conforme au schéma Digest + Markdown brutoutput/digest-*.json, .md
Page Notion des 10 dernières veilles (si configuré)sous la page parente Notion
Mémoire : items publiés, leçon, thèmes, santé des sourcesdata/*.db, .claude/memory/veille.md

Le lanceur bin/veille

bin/veille cycle -k MCP -k agents   # run → digest → [o]ui / [r]ejeter / [p]lus tard → resume
bin/veille pending                  # runs en attente de validation
bin/veille approve <run_id> "note"   # = python -m app.main resume <run_id> --approved --note "note"
bin/veille reject <run_id> "motif"
bin/veille grill                    # entretien Grill-me dans le terminal
bin/veille help

Le lanceur utilise .venv/bin/python (surcharge : VEILLE_PYTHON) et respecte les variables d'environnement (LLM_MODEL=gemma-3-4b-it bin/veille cycle).

🎯 Grill-me : dire ce que tu cherches

Un entretien serré, une question à la fois avec une recommandation : domaines (LLM, nouveaux modèles, robotique, agents, architecture, recherche, événements, outils, réglementation), puis chaque branche choisie. Il te challenge (plus de 3 domaines → priorités ; « tout » → exemple concret). Le profil obtenu (mots-clés, exclusions, sources arXiv suggérées) est mémorisé et guide le Scout et l'Editor. Trois portes d'entrée : l'onglet 🎯 Grill-me (lien direct /#grill-start), « grill me » dans le chat, ou bin/veille grill ; dans Claude Code, le skill /grill-me.

Nouveautés de l'interface (v0.4)

  • Recherche : un ou plusieurs mots-clés (« au moins un » / « tous »), filtres source, dates, statut, limite ; puis « Demander au chat » ou « Lancer une veille ciblée ».
  • Veille ciblée : aussi dans le chat (« relance la veille sur MCP, agents ») et en CLI (run -k MCP -k agents --max-age 7).
  • Surligner / citer : sélectionner un passage d'une réponse, d'un résultat ou d'un digest → 🖍 Surligner ou ❝ Citer dans le prompt.
  • Agents engagés sous chaque réponse (nœuds, outil, agents, skills, MCP, prompts) et lien 🧭 Graphe ↗ vers la trace du parcours.
  • Prompts : édition validée des prompts Scout, Critic, Editor, routeur et système du chat.
  • Rapports : version HTML lisible (et Markdown).

Changer de modèle, y compris vers l'API Claude : voir docs/llm-ollama-claude.md. Déploiement sur Jetson Orin 8 Go : docs/jetson-orin.md.

Instructions Claude templatées

python -m app.main instructions demande --period "semaine 39"   # à coller dans Claude
python -m app.main instructions claude-md --output CLAUDE.generated.md
python -m app.main instructions chat                            # prompt système du chat

Les trois sont rendus depuis templates/claude/profil.toml (domaine, public, thèmes, exclusions, sources, format, outils) : modifier le profil suffit à tout régénérer.

Étape 4

Comment tester

Tests automatiques

python -m pytest -q                                   # unitaires + E2E, hors ligne, ~25 s
RUN_LIVE=1 python -m pytest -q tests/e2e/test_live.py -s  # Ollama + réseau réels (~1 à 2 min)

Les E2E utilisent les vrais serveurs MCP (GitHub et Notion) branchés sur de fausses API HTTP locales, le vrai serveur web FastAPI et de vraies bases SQLite temporaires ; seul le LLM est simulé. Aucun test n'écrit dans data/, reports/ ou votre Notion.

Scénario manuel dans l'interface

  • « Quoi de neuf ? » → outil Dernières veilles, réponse avec citations [n] et cartes sources.
  • « Que disent mes sources sur la quantization ? » → Recherche dans la veille (plein texte), réponse sourcée.
  • « Trouve des nouveaux repos GitHub sur les agents MCP » → GitHub via MCP, dépôts récents.
  • « Lance une veille » → carte « Suivre la progression » ; l'onglet Veille affiche la frise en direct.
  • Onglet Veille → lire le digest, écrire une note, Publier ou Rejeter.
  • Onglet Rapports → le rapport daté du jour s'affiche.
  • « Qu'as-tu en mémoire ? » → la note saisie apparaît parmi les leçons.
  • « Mets à jour la page Notion » → lien vers la page (après l'étape 5).

Une conversation peut être rouverte par son lien : l'URL prend la forme http://127.0.0.1:8000/#c=<id> ; #runs, #reports et #memory ouvrent directement un onglet.

Étape 5 · optionnelle

Publier dans Notion

  1. Créer une intégration interne sur notion.so/profile/integrations et copier son secret (il commence par ntn_).
  2. Dans Notion, créer une page « Veille GenAI » puis, dans son menu ••• → Connexions, ajouter l'intégration.
  3. Copier l'identifiant de la page : les 32 caractères hexadécimaux à la fin de son URL.
  4. Renseigner .env : 
    NOTION_TOKEN=ntn_…
NOTION_PARENT_PAGE_ID=0123456789abcdef0123456789abcdef
  5. Publier : python -m app.main notion-sync (ou « mets à jour Notion » dans le chat).

La sous-page créée contient, pour chacune des 10 dernières veilles : titre, résumé (encadré), description (date, nombre de signaux, sources), ressources (liens) et mots-clés, précédés d'un sommaire. À chaque synchronisation, une nouvelle page est créée et la précédente archivée (récupérable dans la corbeille Notion). Ensuite, chaque veille publiée met la page à jour automatiquement.

Deux serveurs MCP Notionnotion-veille (projet) publie la page ; ses écritures sont bornées à la page parente configurée. Le serveur officiel @notionhq/notion-mcp-server est aussi déclaré dans .mcp.json pour explorer Notion depuis Claude Code (il faut exporter NOTION_TOKEN dans le shell). Toute écriture Notion demandée par Claude passe par une confirmation (hook guard.py).
Étape 6 · optionnelle

Langfuse

Option A — Langfuse Cloud

Créer un projet sur cloud.langfuse.com (région UE ; https://us.cloud.langfuse.com pour les États-Unis), puis Settings → API Keys.

Option B — auto-hébergé

Avec Docker (activer l'intégration WSL de Docker Desktop) :

git clone https://github.com/langfuse/langfuse.git
cd langfuse && docker compose up -d

Interface sur http://localhost:3000.

# .env
LANGFUSE_ENABLED=true
LANGFUSE_PUBLIC_KEY=pk-lf-…
LANGFUSE_SECRET_KEY=…                          # jamais dans Git
LANGFUSE_HOST=https://cloud.langfuse.com       # ou http://localhost:3000

Redémarrer python -m app.main web : la pastille Langfuse passe au vert, et chaque réponse affiche un lien 🔭 Langfuse ↗ vers sa trace. La page /trace/<id> ajoute le lien vers la session (conversation entière ou run). Facultatif : LANGFUSE_PROJECT_ID (réglages du projet) évite un appel API pour construire ces liens.

Étape 7 · optionnelle

LangSmith

Créer une clé dans smith.langchain.com → Settings → API Keys, puis :

# .env
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_…
LANGSMITH_PROJECT=llm-watch-harness
LANGSMITH_ENDPOINT=https://api.smith.langchain.com   # région UE : https://eu.api.smith.langchain.com

L'application recopie ces valeurs dans l'environnement du processus au démarrage : LangChain et LangGraph tracent alors automatiquement vers LangSmith. Langfuse et LangSmith peuvent être actifs en même temps.

Dans Langfuse

  • Lien direct : 🔭 Langfuse sous chaque réponse (trace du tour), et « Session Langfuse » sur la page de trace.
  • Tracing → Sessions : ouvrir la session dont l'id est celui de l'URL #c=… pour relire la conversation tour par tour.
  • Traces, filtre tag chat : repérer les tours lents (latence de respond) ou les routages inattendus (sortie de route).
  • Cliquer la génération ChatOllama : vérifier que le CONTEXTE fourni contenait bien l'information citée.
  • Tag veille : une trace par run, avec scout, critic et editor.

Dans LangSmith

  • Projects → llm-watch-harness → Threads : une ligne par conversation (clé session_id).
  • Runs, filtre sur le tag chat ou veille ; arbre d'exécution par nœud LangGraph.
  • Filtrer par métadonnée model pour comparer gemma et qwen sur les mêmes questions.
  • Ajouter un tour réussi à un dataset pour constituer un jeu d'évaluation.
Méthode conseilléeRejouer la même liste de questions (le scénario de l'étape 4) avec LLM_MODEL=gemma-3-4b-it puis qwen:latest, et comparer dans les deux outils : routage choisi, sources récupérées, citations, latence.
Étape 9

Dépannage

« Ollama injoignable » (pastille rouge)

Lancer ollama serve ou sudo systemctl start ollama, puis curl http://127.0.0.1:11434/api/tags.

« gemma-3-4b-it absent »

Aligner LLM_MODEL sur ollama list. Pour un essai ponctuel : LLM_MODEL=gemma-3-4b-it python -m app.main web.

Première réponse très lente

Chargement du modèle en mémoire GPU. Les suivantes sont rapides tant que le modèle reste chargé (ollama ps).

« Une veille est déjà en cours »

Une seule veille à la fois (GPU partagé). Attendre la fin ou valider le run en cours dans l'onglet Veille.

Notion : « Notion 401 » ou « 404 »

401 : jeton invalide. 404 : la page parente n'est pas connectée à l'intégration (étape 5.2) ou l'identifiant est incorrect.

Rien n'apparaît dans Langfuse / LangSmith

Vérifier les pastilles de l'interface et .env, puis redémarrer le serveur : la configuration est lue au démarrage.
